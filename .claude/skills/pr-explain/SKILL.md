# PR Explain

PR の差分を「前提知識がない人でも読み解ける解説ページ」に変換する。**指摘出しではなく理解が目的**。
バグ探しを頼まれた場合は code review 系の skill を使う。

## 成果物

**プロジェクトのルート直下に `pr-<番号>-explain.html` を1枚生成する**（ブランチ指定なら `pr-<ブランチ名>-explain.html`）。
自己完結した単一HTMLで、外部アセットに依存しない。生成後にファイルパスを伝え、ブラウザで開いてもらう。

- Artifact としては公開しない。ローカルファイルとして渡すだけ。
- 生成物がコミット対象になっていないか確認し、必要なら `.gitignore` への追加を提案する（実際の追記はユーザーの許可を得てから）。
- PR本文へ貼る markdown が欲しいと言われた場合のみ、mermaid フェンスで別途出力する（多くのホスティングは PR 本文の生HTMLをサニタイズするが mermaid は描画される）。

## ガードレール

- **read-only**。この skill の実行中はアプリコードを一切編集しない。書き込んでよいのは生成する解説HTMLのみ。
- PR へのコメント投稿・レビュー登録・push・deploy は**行わない**。投稿はユーザーが明示的に頼んだときだけ。
- 秘匿ファイル（`.env` 系、credentials、鍵、認証情報 JSON）は参照しない。プロジェクトの `AGENTS.md` / `CLAUDE.md` に禁止 path の定義があればそれに従う。
- 常駐プロセスの停止・再起動やコンテナ操作は行わない。差分の理解にテスト実行は不要。
- **推測を断定として書かない**。コードから読み取れないこと（意図・背景・今後の計画）は「PR本文/コミットメッセージによると」と出典を添えるか、`要確認` として明示する。図もコード根拠のある関係だけを描く。

## ワークフロー

### 1. 対象を特定する

```bash
# デフォルトブランチを決め打ちにしない
DEFAULT_BRANCH=$(gh repo view --json defaultBranchRef --jq .defaultBranchRef.name 2>/dev/null \
  || git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|origin/||')
```

| 指定 | 取り方 |
|---|---|
| PR番号 | `gh pr view <N> ...` |
| 現在のブランチ | `gh pr view ...`（PR未作成なら `git diff $DEFAULT_BRANCH...HEAD`） |
| ブランチ名 | `gh pr list --head <branch>` → 無ければ `git diff $DEFAULT_BRANCH...<branch>` |
| コミット範囲 | `git diff <base>...<head>` |

指定がなければ現在のブランチを対象にし、その旨を伝える。`gh` が無い環境では git だけで完結させる。

### 2. 差分の骨格を掴む

```bash
gh pr view <N> --json number,title,body,author,baseRefName,headRefName,additions,deletions,changedFiles

BASE=$(git merge-base origin/$DEFAULT_BRANCH HEAD)
git diff --name-status $BASE..HEAD   # 追加/変更/削除つきの一覧。gh pr diff に --name-status は無い
git diff --stat $BASE..HEAD | tail -5
git diff $BASE..HEAD -- <path>...    # 差分本文。大きい場合は scratchpad のファイルへ
git log --oneline $BASE..HEAD        # コミットの流れ = 作者の思考順
```

コミットメッセージに `Fix ... bug` のような**本題と無関係な修正**が混ざっていることがある。サマリーで「副次」として分離する。

**差分本文は テスト と 非テスト を分けて読む**。非テストだけで構造が掴め、テストは仕様の答え合わせに使う。

**差分が大きい場合（>1,000行 or >20ファイル）**: 探索用の subagent を並列で使い、(a) 変更されたクラス/関数の呼び出し元・既存の類似実装、(b) データ構造・永続化・外部連携への波及、(c) 周辺の設計規約 を分担調査させる。subagent には read-only と担当範囲を明示する。

### 3. ファイルを役割で分類する

行数順ではなく**役割順**に並べ替える。読者は「入口 → 判断 → 中核 → 出力 → データ → 設定」の順で理解する。

| 役割 | 何を探すか |
|---|---|
| 入口 | ルーティング、コントローラ、CLI、ハンドラ、エントリポイント |
| 判断・権限 | 認可、バリデーション、フォーム、ガード |
| 中核ロジック | ドメインモデル、サービス、ユースケース、ジョブ ← **解説の主役** |
| 出力・表示 | ビュー、コンポーネント、シリアライザ、レスポンス |
| データ構造 | スキーマ定義、マイグレーション、型定義、API契約 |
| 設定・定数 | 設定ファイル、環境変数の追加、i18n、フィーチャーフラグ |
| テスト | **仕様の正本**。期待挙動が書いてあるので必ず目を通す |

プロジェクトの言語・フレームワークに合わせて読み替える。分類は「読者が理解する順」を作るための道具であって、分類名そのものが目的ではない。

### 4. プロジェクト固有の高リスク領域を確認する

**まず `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` / `README` を読む**。多くのプロジェクトは「壊すと影響が大きい領域」を明文化している。
差分がそこに触れていたら、解説ページに**専用セクションを立てる**。

明文がない場合、次の観点で自分で判断する。

- **スキーマ / マイグレーション**: 既存データへの影響、反映手順が通常と違わないか
- **監査・履歴の仕組み**: 新モデルの登録漏れがないか
- **外部連携・通知**: 送信先、リトライ、失敗時の挙動
- **バッチ・スケジューラ**: 実行タイミングが変わるか、自動実行か手動か
- **認証・認可**: 誰が何を見られるかが変わるか
- **キャッシュ・派生データ**: 再生成が必要か、順序依存があるか
- **LLM プロンプト**: 出力契約、PII、ガードレール

### 5. 解説の骨組みを作る

**HTMLを書き始める前に、この8項目を埋められるか確認する**。埋まらない項目があるならコードをもう一度読む。

1. **一言でいうと** — 1文。専門用語ゼロ。「〜できるようになる」の形
2. **なぜ必要だったか** — PR本文・チケット・コミットメッセージが出典。無ければ「記載なし（要確認）」
3. **変更サマリー** — 追加/変更/削除を3〜7個の箇条書き。ファイル名ではなく**振る舞い**で書く
4. **登場人物（クラス役割表）** — クラス/モジュールごとに「役割を一言で」「新規か既存か」「誰に呼ばれ誰を呼ぶか」。人に例えた説明を1行添える
5. **関係図** — 登場人物の依存・継承・データの持ち方
6. **処理フロー** — 実際のリクエストやジョブが通る道筋を時系列で
7. **変更前 → 変更後** — 同じ操作が前後でどう変わるかの対比。**ここが理解の核心**
8. **レビューで見るべき順番と注目点** — 読む順にファイルを並べ、各々「なぜここを見るのか」

用語集も作る。**そのプロジェクトのドメイン語**（読者が業務を知らないと分からない言葉）と、このPR固有の新概念を拾う。

### 6. 図を作る

図の型・テーマ両対応・やってはいけないことは `references/diagram-recipes.md` を読む。
最低3枚（関係図・処理フロー・変更前後の対比）。

**図の鉄則**:
- 1枚1メッセージ。詰め込まない
- **変更箇所を色で強調**し、既存部分と区別する（凡例を必ず置く）
- ノード名は実際のクラス名・メソッド名にする。読者が grep できることが重要
- コードに存在しない矢印を描かない
- 図の直後に「この図で言いたいこと」を1〜2文

### 7. HTMLを書いて出力する

1. `artifact-design` skill を読む（必須。デザインの基礎とテーマ対応の指針として使う）。チャートを描くなら `dataviz` も読む
2. ページ構成は `references/page-structure.md` に従う
3. **プロジェクトのルート直下**に `pr-<番号>-explain.html` として書き出す
4. **mermaid は自前で読み込む**。単体HTMLなのでネイティブ描画は効かない。CDN から ESM で読み込み、初期化する

```html
<script type="module">
  import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs';
  mermaid.initialize({ startOnLoad: true, securityLevel: 'loose' });
</script>
```

  オフラインでも開けることを優先するなら、mermaid をやめて図を素の HTML/CSS/SVG で描く。どちらにするかはユーザーに確認せず、
  **ネットワークが使える前提で CDN 版を既定とし、その旨を報告で一言添える**。

5. ユーザーにファイルパスを伝え、**同時にターミナルへ「一言でいうと」＋変更サマリーを出す**。パスだけ渡して終わらない

### 8. 仕上げの自己点検

- [ ] 「一言でいうと」を読んだだけで何のPRか分かるか
- [ ] 図に描いた矢印すべてにコード上の根拠があるか
- [ ] 各クラスの役割説明が、コード内のクラス名の言い換えになっていないか（「UserCreator はユーザーを作る」は説明ではない）
- [ ] 推測と事実が区別されているか
- [ ] ファイル参照が `path/to/file.rb:123` 形式のプレーンテキストか（**リンクにしない**。コピペで辿れれば十分）
- [ ] **横に見切れる要素がないか**。図・表・コードは全て `overflow-x: auto` の親を持ち、中身を中央寄せしていないか（`references/page-structure.md` の「見切れ対策」を参照）
- [ ] 変更前後の対比に、読者が実際に行う操作の言葉が使われているか

## 呼び出し例

```
/pr-explain 1380
/pr-explain                      # 現在のブランチ
/pr-explain main...feature/foo
/pr-explain 1380 PR本文用のmermaidも
```
