# 解説ページの構成

上から読めば理解が積み上がる順。**読者は途中で離脱する**前提で、上ほど情報密度を高くする。

## セクション順

### 0. ヘッダー
PR番号・タイトル・作者・`base ← head`・`+追加 / -削除 / N files`。

### 1. 一言でいうと
1文。専門用語ゼロ。大きめの文字で。「〜できるようになる」の形にする。
補助として比喩を1つ添えてよい（例:「今までは全員が0点スタートだったが、新しい参加者には下駄を履かせる」）。

### 2. なぜ必要だったか
背景・課題。出典（PR本文 / チケット番号 / コミットメッセージ）を明示する。
コードから読み取れない場合は「PR本文に記載なし（要確認）」と正直に書く。**埋めるために想像しない**。

### 3. 変更サマリー
3〜7個。ファイル名ではなく**振る舞い**で書く。

- ✅ 「登録から90日間は、スコアに初期保証分が加算される」
- ❌ 「`initial_point_calculator.rb` を追加」

各項目に該当ファイルの `path:line` を添える。

### 4. 全体像（関係図）
今回の変更がシステムのどこに位置するか。変更箇所を色で強調し、凡例を置く。
図の直後に「この図で言いたいこと」を1〜2文。

### 5. 登場人物
クラス/モジュールごとの表。

| クラス | 状態 | 役割（一言） | 呼ぶ人 → 呼ばれる人 |
|---|---|---|---|

「役割」はクラス名の言い換えにしない。`InitialPointCalculator` を「初期ポイントを計算する」と書くのは説明になっていない。
「登録からの経過日数を見て、まだ新しい対象に加点する係」のように、**何を入力に何を判断するか**を書く。
人に例えた1行（「新人研修期間中の下駄履き担当」）を添えると理解が早い。

### 6. 処理フロー
リクエストやジョブが実際に通る道筋。sequenceDiagram。分岐・非同期・失敗経路も描く。
図の下に、各ステップの補足を番号付きで。

### 7. 変更前 → 変更後
**このページの核心**。同じ操作が前後でどう変わるか。
図での対比＋文章での対比の両方。可能なら具体例（入力値と結果）を数字で示す。

### 8. データ構造の変更
スキーマ・型定義・API契約・派生データに触れている場合のみ。
反映手順が通常と違うなら明記する（独自のマイグレーション方式、監査対象の登録、キャッシュ再生成など）。
触れていない場合はセクションごと省く（「変更なし」と書かない）。

### 9. 気をつける点
高リスク領域への波及、外部連携、通知、パフォーマンス、後方互換。
**事実と懸念を分ける**。懸念は「要確認」ラベルを付ける。

### 10. レビューの読む順番
読む順にファイルを並べ、各々に「なぜここを見るのか」を1行。
テストファイルは最後ではなく、**対応する実装の直後**に置く。

### 11. 用語集
そのプロジェクトのドメイン語（読者が業務を知らないと分からない言葉）＋このPR固有の新概念。
「知らない人がこのページの前半で詰まる語」を拾う。

## ファイル参照の書き方

**リンクにしない。** `path/to/file.rb:123` のプレーンテキストで書く。
等幅フォント・選択しやすい色にしておけば、コピペでエディタから辿れる。
ホスティングの URL を組み立てると、リポジトリ移動・SHA 変更で腐るうえ、読者の手元での再現には役立たない。

## 見切れ対策（最重要）

このページは図・表が多く、**横に見切れる事故が最も起きやすい**。以下を必ず守る。

1. **スクロールの親を1つに決める。** 図・表・コードブロックは `overflow-x: auto` のコンテナに入れ、
   `body` は決して横スクロールさせない。
2. **はみ出す可能性のある中身を中央寄せしない。**
   `display: flex; justify-content: center` の中身が親より広いと、**左側が掴めない位置に切れる**。
   スクロールする箱の中は `justify-content: flex-start` にする。
   ```css
   .diagram { overflow-x: auto; }
   .diagram > .mermaid { display: block; }        /* flex + center にしない */
   ```
3. **mermaid が SVG に付ける `max-width` を外す。** 既定では親幅に縮小され、ER図やノードの多い図が潰れる。
   ```css
   .mermaid svg { max-width: none !important; height: auto; }
   ```
4. **`min-width` を安易に置かない。** 狭い画面で常に横スクロールが出る原因になる。
   置くのは「潰れると意味が壊れる図（メーター、比較表）」だけにする。
5. **テーブルは `white-space: nowrap` を全セルに掛けない。** ヘッダなど短い列だけにする。
6. 書き終えたら **幅 360px 相当で各セクションを見直す**。特にデータ構造・関係図・比較表。

## デザイン

`artifact-design` skill に従う。加えてこのページ固有の要求:

- **ライト/ダーク両対応**（`:root` にライト、`prefers-color-scheme` と `[data-theme]` でダーク）
- 「新規」「変更」「削除」「要確認」はバッジで統一。色＋文字の両方で区別する
- 目次を上部（広い画面では左）に置く。長いページなので現在位置が分かると良い
- 印刷・PDF化されても崩れない（`@media print` で目次を隠し、背景色を保持）
- 単体HTMLとして自己完結させる。CSS と JS はインライン、画像は data URI

## タイトル

`PR#<番号> <主題>` の形。例: `PR#1380 初期保障ポイント`。
説明的な長文にしない。ファイル名は `pr-<番号>-explain.html`。
